## 数据与方法

复用此前独立 manifest：1 个 32GiB 随机大文件、123 个混合文件和 10,000 个 4KiB 文件，共 10,124 个文件、34,524,958,721 bytes。共享上的 `ltfscopytui-20261023/payload` 不包含 manifest；原始 manifest 保留在 tapeserver 本地。

通过 NFS 复制数据时校验本地源 SHA-256，每文件 fsync。随后每种协议分别测 4GiB 顺序写入（含 fdatasync），以及 32GiB `dd iflag=direct` 读取并送入 SHA-256。直接读取只绕过客户端页缓存，不关闭服务器缓存；哈希 CPU 开销包含在读取时间内。混合/小文件副本也独立校验。

只有主机基线均超过 160MB/s 后才启动磁带轮次。每协议将完整 payload 一次追加为 `/nfs-network` 或 `/smb-network`，再完整恢复到对应网络目录，逐文件核对原始 manifest。完整恢复校验替代额外的内置回读，故写任务的 built-in verification 字段应为 not_requested；不把它误报为未验证整个往返。

每个任务保存 endpoint 冻结的真实网络 mount 身份、状态/IPC 大小、吞吐和缓冲采样、原始 C1/CCP 等计数窗口。按协议顺序执行，失败即停，不自动重试覆盖或格式化。

测试日志位于 tapeserver `/home/ain/tapecpy-network-test/results/`。同一份源通过两协议访问，但恢复使用独立目录；结果不能代表 NFS/SMB 的并发一致性测试。小文件部分仅约 39MiB，不能单独证明持续的小文件流式满速。

## 新发现：容量预检固定采用物理分区 0

批量测试首次预检被 90% 容量警告拒绝，尚未创建 runner，未写入数据。原因是 `device::read_mam` 经默认 READ ATTRIBUTE 路径读取物理分区 0；CLI、TUI 和 runner 将该值当作 LTFS 数据可用容量。本卷物理分区 0 实为 index，剩余 36,476MiB；按 label 指定的数据分区 1 单独读取则有 1,352,451MiB。32GiB 单文件恰未超过错误容量的 90%，整批约 32.15GiB 则触发了警告。

这是尚未修复的预检问题；更大的 payload 可能被错误地判定为容量不足，不能只靠确认 warning 解决。应改为按当前可信 LTFS label 的 data_partition 查询容量，查询失败保持 Unknown，不回退到 index 容量。

本轮为保持流式实现与本地基线一致，不在测试中途修改生产代码。通过独立只读探针读取实际数据分区容量、确认足够容纳两轮写入后，显式使用 `--ack-capacity-warning` 继续。保留 `partition-capacity.jsonl`、`preflight-error.txt`、首次中止报告及恢复日志。测试脚本只允许从此种未创建作业的已诊断预检失败恢复，不会自动重试部分写入。

## 已修复：autofs 遮蔽真实网络挂载身份

NFS 写入已成功提交 generation 5，但作业 endpoint 记录成了 `autofs/systemd-1`，被测试断言捕获。根因是 mountinfo 按网络优先排序后，同一路径的真实后端与 autofs 包装不再相邻，而旧实现仅做相邻去重，路径最长匹配又选中了后面的包装。

现改为排序后按 mount point 全局去重，保留优先的真实网络后端。增加 interleaved autofs/NFS/CIFS 回归测试，171 项库测试通过、2 项忽略，Clippy 全目标/全特性通过。该改动仅影响主机挂载解析，不修改流式数据管线。保留 NFS 写入使用的旧二进制及前后 SHA-256，后续恢复和 SMB 作业使用修复版；没有重写已提交的 NFS 数据。新 NFS 恢复 spec 已断言为 `nfs4` 和 `192.168.10.239:/srv/tapecpy-perf`。
